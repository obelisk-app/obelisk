## Where moderation lives

In the old hybrid Obelisk, admins lived in a Postgres table and an admin web panel called an HTTP API to remove people. In the new Obelisk, **the permissions live on the relay**. The admin tools are in the app, but every click publishes a signed NIP-29 event, and the relay is the one that enforces it.

That means:

- Any NIP-29 client can show the same admin list and member list.
- Switching clients doesn't change permissions.
- Switching relays *does*: moderation is per-relay-per-group, because the relay is the enforcer.

## Two kinds of admin

Obelisk has two levels of authority, and they never mix:

- **Channel admins.** A channel is a NIP-29 group. Its admins are the people listed in the relay's latest `39001` event for that group. They manage that one channel.
- **The relay operator.** The pubkey the relay names as its operator (the `contact` npub in its NIP-11 document, else its `pubkey`). Only the operator sees the server settings, and only the operator's events change relay-wide things like roles, categories and branding.

## Channel settings (channel admins)

Open a channel and click its settings in the channel header (on a phone, the channel's settings sheet). From there an admin can:

- **Edit the channel**: name, description, icon and banner.
- **Set who gets in**: *public* (everyone reads and posts), *read-only* (everyone reads, members post) or *private* (hidden, members only).
- **Pick the channel type**: text, voice and video (a peer-to-peer mesh for small rooms), big-room voice (routed through an SFU you choose and verify), or publications (a feed of posts, each with its own chat, with curated tags).
- **Manage members**: add someone by npub or hex key (optionally as an admin), demote an admin to member, or remove someone from the channel.

In the chat itself, an admin can **delete any message** in the channel ("Delete for everyone") and clear its reactions.

## Server settings (relay operator)

The relay operator gets a server settings button at the top of the channel list. It opens five tools:

- **Server profile & banner**: the name, icon, banner and description everyone sees for the relay.
- **Emoji, GIFs & stickers**: the server's own favorites and packs, shown to every member.
- **Channels & categories**: category names and the order of the channels in them.
- **Roles & ranks**: tiered badges (name, color, emoji) shown next to member names. Members can hold several; the most senior one is the badge they wear. Roles are labels, not permissions: the relay still only knows admins and members.
- **Members & moderation**: one table of every admin and member across every channel on the relay, filterable by name, role and channel, to demote or remove people in bulk.

## The events behind the buttons

Every action above is one of these events, signed by the admin and timestamped by the relay. There's no hidden moderation log; the events *are* the log.

| Kind  | What it is                                         |
|-------|----------------------------------------------------|
| `9007`  | Create group: a new channel                       |
| `9002`  | Edit metadata: name, images, access, channel type |
| `9000`  | Put user: add a member, or make them an admin     |
| `9001`  | Remove user: take someone out of the channel      |
| `9003`  | Remove permission: demote an admin to member      |
| `9005`  | Delete event: remove a message or reaction        |
| `39000` | Group metadata, published by the relay            |
| `39001` | Admin list, published by the relay                |
| `39002` | Member list, published by the relay               |

The relay checks each request against its own admin list before it accepts it, and then publishes the updated `39000`/`39001`/`39002` state. Roles, categories and branding are the operator's own replaceable events (NIP-78, kind `30078`), and Obelisk only reads them from the operator's key.

## What about removals across relays?

NIP-29 removals are per-relay. If someone is removed from your group on relay A, nothing stops them from creating a group with the same ID on relay B and posting there. This is by design: relays are sovereign. If you care about portable moderation, run your own relay (or a relay set you control) and replicate group state across them.

## Where the admin CLI went

Earlier versions of Obelisk shipped a Node CLI (`scripts/admin-cli`) that drove an HTTP admin API with an nsec. The API is gone, so the CLI is gone too, and everything it did is now in the app's channel and server settings. A script can still do the same work without Obelisk: load a key with `nostr-tools` or any Nostr SDK, build the NIP-29 events above and publish them to the relay. The relay judges them exactly as it judges a click in the app.
