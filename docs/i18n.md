# Languages

Obelisk ships in **Spanish, English and Portuguese (pt-BR)**. Spanish is the
default; the others are picked per request and then remembered.

Everything a person reads comes from `src/i18n/locales/{es,en,pt}.json` —
flat, dotted keys, one file per language, same keys in all three. There is no
key nesting, no plural machinery and no ICU syntax; `t()` returns a string
and callers substitute with `.replace('{name}', …)`.

## Adding a string

```tsx
const { t } = useTranslation();
…
<button aria-label={t('feed.backToTop')}>{t('feed.backToTop')}</button>
```

Add the key to **all three** locale files in the same position. `locales.test.ts`
fails on a `t('key')` whose key doesn't exist, on a key missing from one
language, and on `{placeholders}` that don't match across languages.

Writing the English straight into the JSX instead fails a different test —
see the ratchet below.

### Copy with markup inside it

A sentence with an element in the middle of it (`Adds a <code>["t","voice"]</code>
tag`) must not be split into three JSX fragments: Spanish and Portuguese put
the element somewhere English doesn't, and a translator can't reorder
fragments. One key with `{slots}`, filled at the call site:

```tsx
import { rich } from '@/i18n/rich';

<p>{rich(t('desktop.channel.voiceHelp'), {
  tag: <code>[&quot;t&quot;,&quot;voice&quot;]</code>,
})}</p>
```

### Dates, times and numbers

Never `toLocaleDateString()`. With no argument it follows the **operating
system**, not the app — so the language picker doesn't change it.

```tsx
const { formatDate, formatNumber } = useFormat();
```

Server-rendered code passes the locale explicitly, from `serverLocale()`:

```tsx
const { t, locale } = await serverLocale();
formatDate(locale, note.created_at, { month: 'short', day: 'numeric' });
```

`src/lib/format.ts` maps our `Locale` union onto BCP-47 through the same
`HREFLANG` table the page head publishes, so the two can't drift.

### On the server

Components use `useTranslation()`, which is client-only. Server components,
and every `generateMetadata`, use `serverLocale()` from
`src/lib/server/locale.ts`. It resolves the locale from the
`x-obelisk-locale` header the proxy sets, falling back to the cookie, then
`DEFAULT_LOCALE`.

Metadata in particular must be `generateMetadata`, not
`export const metadata = {…}` — a static object is evaluated once at module
load, so it cannot depend on who is asking.

## The ratchet

`src/i18n/hardcoded-strings.ts` scans every `.tsx` file for user-visible text
that never reaches a dictionary: JSX text nodes, and the `placeholder` /
`title` / `aria-label` / `alt` / `label` attributes.

`hardcoded-baseline.json` freezes the known set, and the test fails when a
file's count goes **up**, or when a file that had none gains its first. It
started at 654 strings across 80 files.

What's left is exempt on purpose — guide hero SVGs (whose `<text>` also feeds
the OG-image snapshot pipeline), brand names, the media kit's typography and
pitch specimens, and a handful of scanner misreads. The list should only ever
get shorter.

Regenerate after extracting:

```bash
npx tsx -e "import { writeFileSync } from 'node:fs'; \
import { scanTree, countsByFile } from './src/i18n/hardcoded-strings'; \
const c = countsByFile(scanTree('src')); \
writeFileSync('src/i18n/hardcoded-baseline.json', \
  JSON.stringify(Object.fromEntries(Object.entries(c).sort(([a],[b]) => a.localeCompare(b))), null, 2) + '\n');"
```

The scanner can't see copy built with template literals
(`` `Zap ${amount} sats` ``). Those have to be caught by reading.

## Tests need the provider

A component that reads the dictionary needs a `LocaleProvider` around it.
Most test files carry a helper:

```tsx
const renderLocalized = (ui: React.ReactElement) => render(
  <LocaleProvider initialLocale="en">{ui}</LocaleProvider>,
);
```

Two traps: `rerender()` drops the wrapper unless you re-wrap, and a file
calling `vi.resetModules()` must import `LocaleProvider` *dynamically* —
otherwise the provider and the component hold different module instances of
the context and the lookup misses.

## The guides

Long-form articles are MDX under `content/guides/{en,es,pt}/<slug>.mdx`, with
translated frontmatter `title` and `description`. English lives at
`/guides/<slug>`; the others at `/guides/<locale>/<slug>`, so **inline links
inside a translated article must carry the prefix** or they bounce the reader
into English.

A missing translation falls back to the English file rather than 404ing, so
a language can land one article at a time.

## Adding a fourth language

1. `src/i18n/locales/xx.json` — copy `en.json`, translate the values.
2. Add `'xx'` to the `Locale` union and to `LOCALES` in `src/i18n/index.ts`.
3. TypeScript will now point at every `Record<Locale, …>` that needs a row:
   `HREFLANG`, `OG_LOCALE`, the language picker's endonyms, `RelatedGuides`'s
   heading. Fill them in.
4. Optionally map countries to it in `src/i18n/index.ts` for the geo default.
5. `src/app/guides/xx/` — three files, copied from `guides/pt/`.

## Two things are deliberately not translated

- **`src/app/manifest.ts`** is hardcoded Spanish. A static web manifest
  carries one language; pretending otherwise would mean generating it per
  request for no real gain.
- **SEO keyword lists** stay English. They're search terms people type, not
  copy they read.
