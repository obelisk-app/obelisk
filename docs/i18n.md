# Languages

Obelisk ships in **English, Spanish and Portuguese (pt-BR)**, through
[next-intl](https://next-intl.dev). English is the default.

## URLs

The language is in the URL. English has no prefix; the others do:

| | English | Spanish | Portuguese |
|---|---|---|---|
| home | `/` | `/es` | `/pt` |
| app | `/app` | `/es/app` | `/pt/app` |
| a guide | `/guides/vesta` | `/es/guides/vesta` | `/pt/guides/vesta` |

Every page lives under `src/app/[locale]/`. Outside it: `api/`, `dev/`,
`sitemap.ts`, `robots.ts`, `manifest.ts`, `global-error.tsx`, and a
pass-through `layout.tsx` and `not-found.tsx` at the root. `/en/...` redirects
to the unprefixed URL.

**Which language a visitor gets** (`src/proxy.ts`):

1. A prefixed URL is always that language. Visiting it also sets the
   `locale` cookie.
2. An unprefixed URL with a `locale` cookie goes to that language: the
   language the person picked always wins.
3. With no cookie, the CDN's country header and then `Accept-Language` may
   redirect to `/es/...` or `/pt/...` (a 307, since it depends on who asks).
4. With no signal at all (a crawler), the page stays English at `/`, and no
   cookie is written.

The language picker (`LanguageToggle`, `LanguagePreference`) goes to the same
page in the other language through `useSwitchLocale`, keeping the query, and
next-intl writes the cookie as part of that navigation.

Links: always `Link`, `useRouter`, `usePathname`, `redirect` from
`@/i18n/navigation`, which add the prefix. Write hrefs locale-free
(`/guides/vesta`). ESLint bans `next/link` and `next/navigation`'s router,
pathname and redirect outside `src/i18n/`. Code that writes `location` or
`history` directly builds the URL with `localizedPath(locale, path)`
(`src/utils/seo/alternates.ts`) or, in the phone shell, `appShellPath()`
(`src/utils/shell/mobile/url-state.ts`).

## Where copy lives

`src/i18n/messages/<locale>/<module>.json`, one file per module per language,
nested keys. The module is the key's first segment: `chat.composer.send` is
`composer.send` in `messages/en/chat.json`. The modules are listed in
`src/i18n/modules.ts`:

| module | holds |
|---|---|
| `common` | shared words, confirm dialogs, times, deep links, 404, the Google Analytics question (it renders on every page) |
| `seo` | every title, description, social card and JSON-LD text (server only) |
| `marketing` | landing, features, FAQ, roadmap, navbar, footer |
| `showcase` | the `/desktop` and `/mobile` tours |
| `shell`, `mobile` | the desktop and phone app shells |
| `chat`, `dm`, `calls`, `social`, `settings`, `media`, `games`, `voice`, `admin` | the app's features |
| `guides`, `mediaKit` | the guides' chrome, the media kit |
| `help` | the help topics (the `/help` page and the app's help popover) and the `/help/local-data` page, whose category copy Settings > Data on this device reuses (so `/app` ships these, not all of `guides`) |
| `errors` | error codes, activity-log lines and the error panel (see [Errors](#errors)) |

**English is the source of truth.** The key types are generated from the
English files (`src/i18n/types.ts`), so `t('chat.composer.sned')` does not
compile. `tests/i18n/locales.test.ts` fails when es or pt has a different key
set or different ICU arguments than English in any module, on empty values,
on "forum" in any language, and on an em dash.

## Using it

```tsx
import { useLocale, useTranslations } from 'next-intl';

const t = useTranslations();
<button aria-label={t('social.backToTop')}>{t('social.backToTop')}</button>
```

Arguments are ICU, never `.replace()`:

```tsx
t('chat.zap.sendAmount', { amount: formatNumber(locale, sats) })
t('shell.desktop.reactions.count', { count })   // {count, plural, one {# reaction} other {# reactions}}
```

`tests/i18n/call-arguments.test.ts` reads every literal `t('key', {...})` in
`src/` and fails when the object's keys differ from the message's arguments.

A sentence with markup in it is one key with tags, filled with `t.rich`:

```tsx
// "Adds a <tag></tag> tag. Members open <url></url> to join."
t.rich('shell.desktop.channel.voiceHelp', {
  tag: () => <code>["t","voice"]</code>,
  url: () => <code>/voice/{id}</code>,
})
```

A key computed at runtime must still type-check: give the data a
`MessageKey` type (`src/i18n/keys.ts`) or build the template from a union
(`` t(`marketing.steps.${num}.title`) `` with `num: 1 | 2 | 3`). Helpers that
receive `t` take a `Translate`.

**On the server**, `getTranslations({ locale })` from `next-intl/server`, or
`serverLocale()` (`src/services/server/locale.ts`) for `{ locale, t }`.
Server pages and layouts read the segment with `pageLocale(params)`
(`src/i18n/page-locale.ts`), which 404s an unknown locale.

**Outside React**, `translate(key, values?)` from `src/i18n/runtime.ts`.
The app's providers (`src/app/[locale]/app/AppProviders.tsx`) mount
`RuntimeTranslator`, which registers the tree's translator through
`useRegisterTranslator`; until it has (on a public page, or before the app
shell mounts) `translate` returns the key as written, the same fallback
next-intl uses for a missing message. Its callers: the DM call policy's
notices (`src/store/dm-call-policy.ts`), the "sounds are blocked" hint
(`src/services/notifications/alert.ts`), and the notification titles and
bodies the bridge builds (`notifications/classify.ts`, the bridge's
`pings.ts` and `dm/thread.ts`).

Those titles live in **`common.ping`** (`newDm`, `replied`, `repliedIn`,
`mentioned`, `mentionedIn`, `postedIn`), not in `settings` or `shell`:
the marketing `Navbar` imports the bridge (for Disconnect), so the bridge's
whole graph is reachable from every route, and `common` is the only module
every route ships. Any key that code under `src/services/nostr-bridge` names
has to live in `common` for the same reason; `tests/i18n/route-scopes.test.ts`
says so if it does not.

**Dates, times and numbers**: never `toLocaleDateString()` (it follows the
operating system). `useFormat()` in components, `formatDate(locale, ...)` on
the server.

## Errors

Errors are translated by **code**, at the UI boundary, through one
resolver. Nothing below the UI translates: the bridge, the relay hub, the
DM call layer and `src/lib` keep English as the `Error`'s `message` (for the
console, bug reports and the relay debug panel) and carry a code beside it.

**Throwing.** `CodedError` from `src/utils/errors/codes.ts`:

```ts
import { CodedError } from '@/utils/errors/codes';
if (!session) throw new CodedError('not-logged-in', 'Not logged in');
```

The codes are `ERROR_CODES` in that file, one per message under `codes` in
`messages/<locale>/errors.json`; a type check fails the build when the list
and the English file drift apart. A `src/lib` mini-package cannot import the
app, so it gives its own error class a string `code` field with the same
value (`AuthRefusedError.code = 'auth-refused'` in `src/lib/relay-hub`); the
resolver reads any object's `code`. To add one: the message in all three
`errors.json` files, the code in `ERROR_CODES`, then throw it.

**Showing.** `errorText(t, err, fallback?)` from
`src/utils/errors/error-text.ts`:

```ts
import { errorText } from '@/utils/errors/error-text';

catch (e) { setError(errorText(t, e, 'chat.composer.sendFailed')); }
```

Give every call a fallback key that names the action (`'chat.relayForm.addFailed'`,
`'shell.channel.createFailed'`, ...): a relay's or an extension's words
are English, and without a fallback they would reach the screen as they
came. Under a title that already says what failed (a toast), the body is
`errorReason(t, err)`: the code's sentence, or nothing.

- an error with a known code (or a bare code string, such as the suffix of
  an `Error:<code>` connection state) reads `errors.codes.<code>`;
- otherwise the `fallback` key, when given, so the screen stays in one
  language;
- otherwise the error's own message (a relay's or an extension's words,
  which we cannot translate), or `errors.generic` when it has none.

Replace `(e as Error).message` with it wherever an error reaches a toast, a
banner or a form. The resolver reads the `errors` module, so the route must
ship it: `/app` and the viewers (`/notes`, `/p`, `/t`, for the reply
composer) do; any other route that starts calling it adds `errors` to its
scope in `src/i18n/modules.ts`. Import it from `@/utils/errors/...`, not
through the bridge: a test that fakes `@/services/nostr-bridge` would fake it
away (the bridge re-exports the code types only).

**The activity log.** The bridge pushes activity entries whose `label` is
an `ActivityCode` (`publish`, `signBunker`, `relayAuth`, ...) and whose
`description` is an `EventKindLabel` (`message`, `dm`, ...). While an entry
runs its `detail` is data (a relay host or URL list); when it fails, an
error code or the relay's own words. `activityTitle` and `activityDetail`
(`src/utils/errors/activity-text.ts`) read them as
`errors.activity.<code>.<status>` (with `{target}`, the detail) and
`errors.kinds.<label>`; an entry with English in those fields is printed as
it is.

**The error panel** (`src/components/feedback/ErrorPanel.tsx`) renders under
`global-error.tsx`, where no provider exists. It imports the three
`errors.json` files directly, reads its language off `<html lang>`, and
formats with next-intl's context-free `createTranslator`. A coded error also
gets its reason line; the English message stays in "Error details".

**Out of scope for codes**: messages nobody reads (subscription close
reasons, publish row reasons, relay debug lines, corrupt-storage errors that
are erased silently). They stay English, and a line the scanner would flag
carries `i18n-exempt: <reason>`.

## What reaches the browser

Only the active language, and only the modules a route renders. Each route
wraps its client tree in `<IntlScope scope="...">` (`src/i18n/IntlScope.tsx`),
which ships the modules in `SCOPES[scope]`: the landing page gets `common` and
`marketing`, `/app` everything but the public-page modules, and `seo` never
leaves the server. `tests/i18n/route-scopes.test.ts` walks every file a route
can load and fails when one reads a module its scope does not ship (the raw
key would show). If you add a key to a component, add it to a module its
routes already ship, or add the module to the scope.

## SEO

Full write-up and the per-route decisions: `audits/obelisk/round24/seo.md`
(outside the repo). The short version:

- **One builder.** Every page's metadata comes from `pageMetadata` or
  `noindexMetadata` (`src/utils/seo/page.ts`; most pages through
  `standardPageMetadata`, `src/utils/seo/standard.ts`). Next.js replaces
  `openGraph`, `twitter` and `robots` wholesale when a page sets them, so a
  page that builds them by hand loses pieces; that is how pages lost their
  image, `og:site_name` and `og:url` before.
- **Copy.** Titles and descriptions are `seo.<page>.title` / `.description`
  in the page's language; guides use their front matter's `seoTitle` /
  `seoDescription` (the `description` is the lede on the page). The rendered
  title, " · Obelisk" included, is 45 to 57 characters and the description
  145 to 157, in all three languages; the card (`og:*`, `twitter:*`) repeats
  the same two strings. Keyword lists stay English: they are search terms.
- **Canonical and hreflang.** The canonical is the page in its own
  language. `hreflang` lists `en`, `es`, `pt` and `x-default` (English): the
  plain language, because one Spanish version serves every Spanish-speaking
  country (a region code such as `es-AR` would send a reader in Mexico to
  English). `og:locale` needs a territory and names the variety the copy is
  written in (`es_AR`, `pt_BR`); dates and numbers format with the same
  regional tags (`INTL_LOCALE` in `src/utils/format/format.ts`).
- **Indexed:** `/`, `/features`, `/desktop`, `/mobile`, `/help`,
  `/help/local-data`, `/media-kit`, `/guides` and every guide, in each
  language; exactly the sitemap. **Not indexed** (`noindex, follow`, no
  canonical or hreflang, still a full card): `/app`, `/voice`, share links
  `/r/<code>`, and the relay-content viewers `/notes`, `/p`, `/t`. A malformed
  note or profile id is a 404.
- **Cards.** Every page has its own 1200x630 PNG: an `opengraph-image.tsx`
  in its route folder, drawn by `src/components/seo/OgCard.tsx` (the guides
  keep `guide-og-image.tsx`) from text in `src/services/server/og-cards.ts`.
  Metadata names the card at the page's public URL (`cardImage`,
  `src/utils/seo/og.ts`); the file convention alone would point at the
  internal `/en/...` route.
- **JSON-LD.** WebSite and Organization (La Crypta, by `@id`) on every page;
  WebApplication and FAQPage on the landing page; CollectionPage and
  BreadcrumbList on the guides index; Article and BreadcrumbList on a guide,
  dated from front matter. Builders in `src/utils/seo/jsonld.ts` and
  `guide.ts`.
- **Sitemap and robots.** `lastmod` is a guide's `updatedAt`, the guides
  index's newest guide, or absent; never the build time. robots.txt blocks
  `/api/` and `/dev/` only: a noindex page must stay crawlable for its
  noindex to be read.
- **Crawlers** and link-preview bots are never language-redirected by the
  proxy (`isCrawler`, `src/utils/seo/crawler.ts`).

`npm run seo:check` builds, starts the server and crawls every route the way
the bots do; it fails on any of the above. Run it before shipping anything
that touches metadata, copy in `seo`, guide front matter or routes.

## The ratchet

`src/i18n/hardcoded-strings.ts` (rules in `src/i18n/hardcoded/`) finds copy
that never reached a message file: JSX text (read from the TypeScript syntax
tree, `hardcoded/jsx-text.ts`, so a paragraph that wraps lines or is split by
`{' '}`, `<strong>`, `<a>` or an `{expression}` is one sentence), string
props (below), the expressions inside reader-facing attributes, copy-shaped
object keys, toast and dialog arguments, ternaries, `|| 'fallback'`,
capitalised template literals, `.ts` files, and any prose literal in
`src/lib` (a mini-package exports codes). Comments are stripped first.

**String props.** A plain string given to any JSX attribute, of an HTML
element or a custom component, is copy when it reads as prose:
`<SettingRow subtitle="Shown to everyone">`, `description="..."`,
`emptyText="..."`, `heading={'...'}`, `` label={`...`} `` (a template with no
`${}`). `hardcoded/jsx-attrs.ts` reads them from the syntax tree; anything
computed (`t()`, a variable) is left alone, and a ternary of strings is the
`ternary` rule's. The attributes that never carry reader-facing text are
skipped by name (`SKIP_ATTRS`), each group for a value the repo has that
would otherwise read as prose:

| skipped | why |
|---|---|
| `className`, `class`, `style`, `id`, `key`, `testId`, `data-*` | styling and identity (`className="screen active"` is a class list with no dash) |
| `href`, `src`, `srcSet`, `allow` | where a resource lives, what an iframe may do |
| `type`, `name`, `role`, `rel`, `target`, `method`, `as`, `htmlFor`, `autoComplete`, `inputMode`, `lang`, `dir` | HTML enumerations and form plumbing (`rel="noopener noreferrer"`) |
| `variant`, `size`, `tone` | the design system's variant props |
| `d`, `path`, `transform`, `preserveAspectRatio` | SVG geometry (`d="M19 6l-1 14a2 2 0 01-2 2H8"`) |
| `on*` | event handlers |

Every other enum-valued prop in the repo (`fill`, `align`, `side`, `surface`,
`placement`, `kind`, `icon`, ...) holds single lowercase tokens that the prose
check already rejects, so it is not listed. Add a name only for a value that
is not copy and still reads as prose, and say why beside it.

`hardcoded-baseline.json` freezes what is left and only shrinks: a new file
with copy, or a file gaining some, fails. It has been empty since
2026-10-06 (it started at 598 strings in 171 files), so today any new
hardcoded copy fails. Regenerate after moving strings, never hand-merge:

```bash
npx tsx scripts/i18n/hardcoded-baseline.ts          # rewrite the baseline
npx tsx scripts/i18n/hardcoded-baseline.ts --list components/chat   # see what is left
```

Text that legitimately stays carries `i18n-exempt: <reason>` in a comment
on its line: brand names, protocol terms and wire payloads drawn as code
(`kind 2390`, `op: attack`), type specimens. The reason is required. For JSX
text that spans lines, the marker may sit on any line of the sentence or on
its parent's opening tag (`<div> {/* i18n-exempt: type specimen */}`); it
covers that sentence only, not a sibling element. For a string prop it sits
on the prop's line, as a comment inside the tag
(`hint="NIP-29 kind 9000" /* i18n-exempt: protocol term */`), and covers that
prop only.

Guide artwork is not exempt as such. The heroes and diagrams read their
labels from `guides`, and the OG snapshots are rendered once per language
(`public/og/guides/<file>` for English, `public/og/guides/{es,pt}/<file>`
for the others; `snapshotPaths(name, locale)` in
`src/utils/guides/asset-meta.ts`), so a guide's card, its page and its
sitemap entry all show the artwork in that guide's language.

## Tests

`LocaleProvider` from `@tests/support/intl` wraps a component in a
`NextIntlClientProvider` with every module of one language; a missing key or
a missing argument throws. `translator('es')` gives a plain `t` for
non-React assertions. `next-intl/server` is replaced in vitest by
`tests/support/next-intl-server.ts`, and `IntlScope` by a synchronous
stand-in, so `render(await Page({ params }))` works. A test that watches
navigation mocks `@/i18n/navigation` with
`@tests/support/mocks/i18n-navigation`.

## The guides

MDX under `content/guides/{en,es,pt}/<slug>.mdx`, same slugs in every
language, translated frontmatter. One route tree:
`src/app/[locale]/guides/[slug]`. Inline links are written locale-free
(`/guides/web-of-trust`); the MDX `a` component routes them through the
locale-aware `Link`. A missing translation falls back to the English file.
The old `/guides/es/...` and `/guides/pt/...` URLs (OG images included)
308-redirect to the new ones (`next.config.ts`).

## Adding a fourth language

1. `src/i18n/messages/<code>/` (say `xx`): copy the `en` folder, translate the values.
2. Add `'xx'` to `LOCALES` in `src/i18n/index.ts`.
3. TypeScript points at every `Record<Locale, ...>` that needs a row
   (`HREFLANG`, `OG_LOCALE`, `INTL_LOCALE`, the pickers' endonyms). Fill them in.
4. Add the prefix to `LOCALE_PREFIX_RE` in `public/sw.js` and to the
   `/:locale(es|pt)/chat` redirects in `next.config.ts`.
5. Optionally map countries to it in `src/i18n/index.ts`.
