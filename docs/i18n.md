# Languages

Obelisk ships in **English, Spanish and Portuguese (pt-BR)**, through
[next-intl](https://next-intl.dev). English is the default.

## URLs

The language is in the URL. English has no prefix; the others do:

| | English | Spanish | Portuguese |
|---|---|---|---|
| home | `/` | `/es` | `/pt` |
| app | `/app` | `/es/app` | `/pt/app` |
| a guide | `/guides/vesta` | `/es/guides/vesta` | `/pt/guides/vesta` |

Every page lives under `src/app/[locale]/`. Outside it: `api/`, `dev/`,
`sitemap.ts`, `robots.ts`, `manifest.ts`, `global-error.tsx`, and a
pass-through `layout.tsx` and `not-found.tsx` at the root. `/en/...` redirects
to the unprefixed URL.

**Which language a visitor gets** (`src/proxy.ts`):

1. A prefixed URL is always that language. Visiting it also sets the
   `locale` cookie.
2. An unprefixed URL with a `locale` cookie goes to that language: the
   language the person picked always wins.
3. With no cookie, the CDN's country header and then `Accept-Language` may
   redirect to `/es/...` or `/pt/...` (a 307, since it depends on who asks).
4. With no signal at all (a crawler), the page stays English at `/`, and no
   cookie is written.

The language picker (`LanguageToggle`, `LanguagePreference`) goes to the same
page in the other language through `useSwitchLocale`, keeping the query, and
next-intl writes the cookie as part of that navigation.

Links: always `Link`, `useRouter`, `usePathname`, `redirect` from
`@/i18n/navigation`, which add the prefix. Write hrefs locale-free
(`/guides/vesta`). ESLint bans `next/link` and `next/navigation`'s router,
pathname and redirect outside `src/i18n/`. Code that writes `location` or
`history` directly builds the URL with `localizedPath(locale, path)`
(`src/utils/seo/alternates.ts`) or, in the phone shell, `appShellPath()`
(`src/utils/shell/mobile/url-state.ts`).

## Where copy lives

`src/i18n/messages/<locale>/<module>.json`, one file per module per language,
nested keys. The module is the key's first segment: `chat.composer.send` is
`composer.send` in `messages/en/chat.json`. The modules are listed in
`src/i18n/modules.ts`:

| module | holds |
|---|---|
| `common` | shared words, confirm dialogs, times, deep links, 404 |
| `seo` | every title, description, social card and JSON-LD text (server only) |
| `marketing` | landing, features, FAQ, roadmap, navbar, footer |
| `showcase` | the `/desktop` and `/mobile` tours |
| `shell`, `mobile` | the desktop and phone app shells |
| `chat`, `dm`, `calls`, `social`, `settings`, `media`, `games`, `voice`, `admin` | the app's features |
| `guides`, `mediaKit` | the guides' chrome, the media kit |
| `errors` | error codes resolved at the UI boundary (filled by the next wave) |

**English is the source of truth.** The key types are generated from the
English files (`src/i18n/types.ts`), so `t('chat.composer.sned')` does not
compile. `tests/i18n/locales.test.ts` fails when es or pt has a different key
set or different ICU arguments than English in any module, on empty values,
on "forum" in any language, and on an em dash.

## Using it

```tsx
import { useLocale, useTranslations } from 'next-intl';

const t = useTranslations();
<button aria-label={t('social.backToTop')}>{t('social.backToTop')}</button>
```

Arguments are ICU, never `.replace()`:

```tsx
t('chat.zap.sendAmount', { amount: formatNumber(locale, sats) })
t('shell.desktop.reactions.count', { count })   // {count, plural, one {# reaction} other {# reactions}}
```

`tests/i18n/call-arguments.test.ts` reads every literal `t('key', {...})` in
`src/` and fails when the object's keys differ from the message's arguments.

A sentence with markup in it is one key with tags, filled with `t.rich`:

```tsx
// "Adds a <tag></tag> tag. Members open <url></url> to join."
t.rich('shell.desktop.channel.voiceHelp', {
  tag: () => <code>["t","voice"]</code>,
  url: () => <code>/voice/{id}</code>,
})
```

A key computed at runtime must still type-check: give the data a
`MessageKey` type (`src/i18n/keys.ts`) or build the template from a union
(`` t(`marketing.steps.${num}.title`) `` with `num: 1 | 2 | 3`). Helpers that
receive `t` take a `Translate`.

**On the server**, `getTranslations({ locale })` from `next-intl/server`, or
`serverLocale()` (`src/services/server/locale.ts`) for `{ locale, t }`.
Server pages and layouts read the segment with `pageLocale(params)`
(`src/i18n/page-locale.ts`), which 404s an unknown locale.

**Outside React** (the DM call policy, the notification sound hint),
`translate()` from `src/i18n/runtime.ts`; the app shell lends it its
translator (`RuntimeTranslator`).

**Dates, times and numbers**: never `toLocaleDateString()` (it follows the
operating system). `useFormat()` in components, `formatDate(locale, ...)` on
the server.

## What reaches the browser

Only the active language, and only the modules a route renders. Each route
wraps its client tree in `<IntlScope scope="...">` (`src/i18n/IntlScope.tsx`),
which ships the modules in `SCOPES[scope]`: the landing page gets `common` and
`marketing`, `/app` everything but the public-page modules, and `seo` never
leaves the server. `tests/i18n/route-scopes.test.ts` walks every file a route
can load and fails when one reads a module its scope does not ship (the raw
key would show). If you add a key to a component, add it to a module its
routes already ship, or add the module to the scope.

## SEO

Every `generateMetadata` reads `seo.*` in the page's language and spreads
`localizedAlternates(locale, path)` (`src/utils/seo/alternates.ts`): the
canonical is the page in its own language, and `alternates.languages` lists
`en-US`, `es-AR`, `pt-BR` and `x-default` (English). User content (`/notes`,
`/p`, `/t`) points every language's canonical at the English URL. OpenGraph
carries `og:locale` and the other two as `alternateLocale`; `<html lang>` and
JSON-LD `inLanguage` follow the URL. The sitemap lists every page in every
language with the same four alternates. The layout sets no canonical, so a
page that forgets its own does not inherit `/`.

Keyword lists stay English: they are search terms people type, not copy.

## The ratchet

`src/i18n/hardcoded-strings.ts` (rules in `src/i18n/hardcoded/`) finds copy
that never reached a message file: JSX text, reader-facing attributes and
the expressions inside them, copy-shaped object keys, toast and dialog
arguments, ternaries, `|| 'fallback'`, capitalised template literals, `.ts`
files, and any prose literal in `src/lib` (a mini-package exports codes).
Comments are stripped first.

`hardcoded-baseline.json` freezes what is left (598 strings in 171 files on
2026-10-06) and only shrinks: a new file with copy, or a file gaining some,
fails. Regenerate after moving strings, never hand-merge:

```bash
npx tsx scripts/i18n/hardcoded-baseline.ts          # rewrite the baseline
npx tsx scripts/i18n/hardcoded-baseline.ts --list components/chat   # see what is left
```

Text that legitimately stays carries `i18n-exempt: <reason>` in a comment
on its line: brand names, protocol terms, guide hero artwork (it is rendered
into the OG snapshot PNGs), type specimens. The reason is required.

## Tests

`LocaleProvider` from `@tests/support/intl` wraps a component in a
`NextIntlClientProvider` with every module of one language; a missing key or
a missing argument throws. `translator('es')` gives a plain `t` for
non-React assertions. `next-intl/server` is replaced in vitest by
`tests/support/next-intl-server.ts`, and `IntlScope` by a synchronous
stand-in, so `render(await Page({ params }))` works. A test that watches
navigation mocks `@/i18n/navigation` with
`@tests/support/mocks/i18n-navigation`.

## The guides

MDX under `content/guides/{en,es,pt}/<slug>.mdx`, same slugs in every
language, translated frontmatter. One route tree:
`src/app/[locale]/guides/[slug]`. Inline links are written locale-free
(`/guides/web-of-trust`); the MDX `a` component routes them through the
locale-aware `Link`. A missing translation falls back to the English file.
The old `/guides/es/...` and `/guides/pt/...` URLs (OG images included)
308-redirect to the new ones (`next.config.ts`).

## Adding a fourth language

1. `src/i18n/messages/xx/`: copy the `en` folder, translate the values.
2. Add `'xx'` to `LOCALES` in `src/i18n/index.ts`.
3. TypeScript points at every `Record<Locale, ...>` that needs a row
   (`HREFLANG`, `OG_LOCALE`, the pickers' endonyms). Fill them in.
4. Add the prefix to `LOCALE_PREFIX_RE` in `public/sw.js` and to the
   `/:locale(es|pt)/chat` redirects in `next.config.ts`.
5. Optionally map countries to it in `src/i18n/index.ts`.
