# Concord integration

Status: implementation in progress on `feat/concord-dual-protocol`. This document describes the code present, not a claim of production readiness or complete protocol parity.

## Ownership

Each community uses either NIP-29 or Concord. There is no message bridge between them. Existing NIP-29 relay selection and admission remain unchanged. The existing + menu keeps the ordinary relay flow and offers a separate Add a Concord community action, followed by create/join actions. There is no encryption-mode switch for NIP-29 relays. Joined communities and NIP-29 relays share one alphabetically ordered rail without protocol sections. Concord rail tiles subscribe to authenticated community images and update when the profile image changes. On phones there is no horizontal community rail: the existing relay switcher includes both kinds of community, using the same deck interactions and each community's branding. Conversations render in the normal desktop or phone shell, using the existing channel rows, header, message rows, menus and composer. Phone chat reuses ChannelHeaderBar, ChannelTimeline/ChannelMessage and ChannelComposer; channel/community settings and members use shared sheets. The channel Back button opens the full community channel screen rather than a second header above chat. Only setup and administration use dialogs. The channel-header gear edits the selected channel name using an expected-edition guard, preserving its privacy and custom fields. The community-header gear opens community settings. Main community settings use the ordinary settings menu with supported destinations for appearance, categories, channels, roles, members and invitations. Editors have shared Back headers instead of mixing their fields into the menu. The sidebar reuses `SidebarHeader` for its banner, icon and title, and `CreateGroupSection` for its visible + channel control. The existing appearance picker stages images locally; Save sends them through the encrypted SDK uploader, and authenticated image bytes are displayed using temporary object URLs. Route-owned integration lives in `src/app/[locale]/app/concord/`.

`src/services/nostr-bridge/concord/` owns the lazy, per-session Concord runtime. Its public entry is `getConcordForBridge` through the bridge front door. The SDK is the MIT-licensed `@applesauce/concord` snapshot `0.1.0-dev.00ceaa38355d`, vendored with the acknowledged staff-Grant publication fix as `vendor/applesauce-concord-00ceaa38355d-obelisk.1.tgz` from the Accordion reference client's dependency. The upstream revision is `00ceaa38355d6d3cbc1f7c859c0e1d5eae71e841`. The reference application's source is not copied.

`hub-socket.ts` provides the SDK's WebSocket interface over Obelisk's RelayHub. Actual sockets belong to the hub. Concord uses a separate `concord:<pubkey>:<generation>` identity with no AUTH signer and `never-auth` policy. This deliberately does not authenticate the person's account to community relays. Relays requiring AUTH are not supported by this transport yet. NIP-77 requests receive an unsupported response so the SDK can fall back to paginated Nostr REQ.

Creation requires exactly three distinct secure WebSocket relay URLs. Defaults live in `src/constants/nostr-bridge/concord.ts`. Imported communities retain the relay set defined by their protocol state. This is a Concord-specific exception to the NIP-29 single-active-relay rule, not permission to expand existing group subscriptions.

## Navigation

The address bar uses `/app#concord=<community-id>&channel=<channel-id>` (with the current locale prefix when present). Routing identifiers live in the fragment, not the request query; invitation secrets and encryption keys are never included. The old NIP-29 relay/channel coordinates are removed while viewing Concord. Reload and browser Back restore the indicated community and channel, ahead of the encrypted last-view cache. These are navigation links for existing members, not invitations granting membership. Both shells yield URL ownership and clear their watched NIP-29 channel while a Concord community is displayed.

The desktop community rail and mobile switcher use the same tile and card
presentations for both protocols. Mobile channel rows are also shared.
Protocol adapters still own selection, unread state and permissions.

The public invite card uses generic Obelisk artwork. Community icon and
banner pointers remain in encrypted community metadata. After an authorized
client opens an image, it can retain the authenticated ciphertext in its
bounded account cache. Blossom retention is independent of encryption.
Previously deleted blobs require a surviving cached copy or a new upload.

## Cross-device recovery

The SDK publishes its protocol-standard Community List fragments (kind 33302; legacy kind 13302 is read for interoperability), encrypted to the account itself through NIP-44. The list contains memberships and the key material needed to reopen them, not plaintext messages. Creation/join/leave explicitly save the list; `autoSaveCommunityList` persists subsequent key changes. On startup the SDK reconciles its local encrypted mirror with relay fragments before auto-saving, preserving its own merge and concurrency guards.

These account recovery events use the signed-in user's discovered inbox/read relays plus the three previous compatible defaults in `CONCORD_DEFAULT_RELAYS` for migration. They are not sent to other users' inboxes or across the configured NIP-29 community rail. Community events continue to use the community's chosen relays. A second device signs in with the same Nostr identity and a signer supporting NIP-44, restores the list, and fetches community state/messages from those community relays. The phone switcher lists recovered communities. Selecting one opens its community channel list and banner, matching NIP-29; chat opens only after choosing a channel. This switcher intent is separate from the SDK's default channel selection and also works when reselecting the current community. Relay availability and retained ciphertext remain prerequisites; a different Nostr key does not recover another account's communities.

The last selected channel, open pane, drafts and decrypted media are not synced through this list. Navigation remains sealed locally; decrypted media stays in disposable memory URLs. No new plaintext localStorage backup, custom key-export link or authority-check bypass is introduced.

## Storage and lifecycle

The runtime supplies encrypted SDK storage explicitly; it does not use the SDK's default localStorage persistence. IndexedDB `obelisk-concord`, object store `sealed`, holds authenticated ciphertext under an account-specific non-extractable vault key named `concord-key:<pubkey>`. Record names hash SDK keys so community identifiers are not embedded directly in cache addresses. Decrypted community state and timelines stay in runtime memory. The last selected community, channel and whether its pane is open are stored under the encrypted `obelisk/navigation` record. They restore after sign-in without overwriting a new selection or an incoming invitation. Startup exposes the SDK's locally restored communities as soon as they are available instead of awaiting relay reconciliation; encrypted plane snapshots feed the normal state fold and message timelines while synchronization continues. The SDK still owns validation, key transitions and publication guards. A separate readiness promise reports background startup failures. Membership storage is unchanged; a deployment does not clear it.

Rumor stores persist encrypted plane snapshots and reject growth beyond 100,000 events or 32 MiB per plane. They must fail closed rather than silently truncate authority history. Session guards reject work after account invalidation; disposal closes SDK subscriptions and removes the isolated hub identity. This storage is listed in the local-data inventory. It does not use `bridgeCache`, which stores ordinary relay-derived data in localStorage.

## Implemented surface and remaining work

The current shared chat surface has create/join forms, channel creation and selection, text sending, reactions, deletion projection and invitation generation. Clicked Concord invitations are routed through the app fragment, held only in memory, and removed from the address bar after sign-in. The invitation landing uses a full document navigation into the localized app so its CSP nonce changes with the document; the fragment is captured before login and retained until authentication. English, Spanish and Portuguese strings live in each locale's `chat.concord` subtree. Forms use the shared form model and primitives.

Channel creation supports private channels and the native Publications view. Categories use the optional community `custom.obelisk.layout` extension, migrating older per-channel `custom.obelisk.category` names; updates preserve unknown fields and guard the selected edition head against concurrent edits. Other clients may ignore this extension. Role creation and assignment use the SDK's authority checks. Invite and deletion controls are capability-aware. Private channels without a held key are disabled. The initial ban action requires completed SDK Refounding and requires explicit review of retained readers for each private channel before rotating its key; it must not claim read-access revocation from a Banlist edit alone.

Attachments use independent AES-256-GCM keys and 16-byte nonces, carried only inside encrypted imeta. Only ciphertext goes to the existing encrypted Blossom uploader. Ciphertext reads are bounded to 25 MiB plus the GCM tag, authenticated and checked against available hashes. Supported raster images, video and audio decrypt into disposable memory URLs and render with the normal media controls. Other files require an explicit download. Ciphertext URLs in message text are replaced by their attachment presentation, and timeline projection deduplicates rumor IDs from multiple relays. A synchronous send guard prevents repeated Send/Enter actions from starting another upload while the first encrypted send is pending. Decrypted attachments are never added to a persistent cache.

Concord sends enter a bounded, memory-only outbox immediately. The normal message row displays the selected photo through a local blob preview with Preparing, Uploading and Sending states; the composer clears as soon as the outbox accepts it. A failed upload or missing relay acknowledgement keeps that row and its Retry/Dismiss controls. Retry retains completed encrypted uploads and republishes the same prepared rumor, including its timestamp, so partial relay delivery does not create a second message. The SDK's required-ack publication path replaces the pending row only after a relay accepts it. Cached rooms can paint before the SDK finishes reconciling keys; sends remain pending until its community phase becomes live. A bounded wait fails into the existing Retry action rather than publishing with stale keys. Repeated Retry clicks are ignored while sending. Runtime disposal revokes previews and prevents an unfinished upload from publishing under a later session. Pending files are intentionally not persisted: reloading before delivery loses an unsent file, while delivered history still uses the sealed cache.

The fixed mobile shell uses clipped overflow so focus cannot scroll its oversized background and displace the header. Only inner message lists and sheets scroll. Mobile Concord sheets live inside the same positioned screen container as NIP-29 sheets, above the channel screen and within the space above bottom navigation. The community banner reuses the normal relay-status, search, authorized channel-add and menu layout. Relay diagnostics observe existing Concord identity sockets without probing or authenticating as the account. Desktop and phone search cover channel names and authenticated locally loaded history across accessible community channels. Search never sends plaintext queries to relays and does not claim complete remote history.

Channel settings edit name, parent and the Publications view under a metadata edition guard. Categories and their ordering use the shared category editor described below, preserving empty categories and explicit order. Removing a category returns its channels to Uncategorized. Category/order metadata remains an Obelisk extension and is not guaranteed to render identically in other Concord clients.

Cross-client category/publication interoperability, broader private-channel rekeying validation, staff reports, search, notifications, games and CORD-07 voice are not yet verified or complete. The original pinned SDK rejected staff Grants after its own optimistic local echo. The Obelisk vendor patch routes these Grants through the existing required-ack publication path, which echoes after publication. Authority, material and selected-head guards remain unchanged. Role administration and moderation still require broader browser and cross-client coverage. Do not describe this implementation as full Concord parity until these paths and cross-client interoperability are tested.

## Shared component protocol boundary

`ChannelProtocolContext` routes composer send/upload, reactions and deletions to Concord. Absence of that context preserves the existing NIP-29 path. Encrypted uploads are bounded in memory and passed to the SDK uploader at send time; plaintext never enters the public Blossom uploader. Private message bodies do not auto-unfurl arbitrary URLs or load public game/media previews; only authenticated imeta attachments enter the encrypted media renderer. Public event links, forwarding and zaps are unavailable for private message IDs. Local search and full Publications parity remain follow-up work.

## Account recovery and channel organization

Encrypted account configuration now covers NIP-29 community relay connections and per-channel follow, mute and notification preferences as well as Concord membership recovery. `account-data/sync.ts` stores a signed kind 30078 record with `d=obelisk:community-connections:v1`, NIP-44 encrypted to the signed-in account itself. The destination is that account's kind 10050 inbox, then its NIP-65 read relays, with public fallback relays only when neither list exists. It never sends NIP-29 messages or performs account AUTH on these sockets. Restoring a rail entry does not connect to that community or grant membership; the NIP-29 relay still enforces admission. The existing per-device channel preference cache is retained; the sync snapshot is sealed in IndexedDB.

Updates merge timestamped entries and removal tombstones. A fresh browser reads before publishing defaults. Offline reads do not clear preferences. Failed publishes retry, and account disposal stops the sync. These configuration records are separate from Concord's SDK Community List, which contains membership/key recovery data. Concord's personal list now uses the account inbox/read relays plus the previous default destinations for migration. Community messages still use the community's chosen relays. Relays requiring account AUTH cannot currently receive this never-auth sync.

Channel forms support parent channel and Publications; category assignment and order are managed in the shared layout editor. The Obelisk parent extension rejects cycles and missing parents; imported invalid relationships render as roots. Voice is unsupported. Publications reuse the ordinary desktop and mobile list/composer: a titled Concord kind 9 is a publication, NIP-22 kind 1111 events are comments, and the local thread ID is only a UI projection. The URL retains the selected thread. Other Concord clients need not display Obelisk's categories or parent tree.

Right-clicking a Concord rail tile opens the shared anchored menu to switch, copy its community ID or leave after confirmation. Leaving removes the saved membership rather than deleting the community. Pending media and its matching relay echo render as one row until the required acknowledgement arrives.

## Member channel creation

The community owner can enable **Members can create and manage channels** in community settings > Roles. Existing and new members then receive a normal CORD-04 server role with only `MANAGE_CHANNELS`, at position 4294967294. Concord bundles creation, editing and deletion in this permission; the setting explains that scope. Other administrative capabilities, including role management, banning and category layout, are not granted. Existing communities stay unchanged until the owner enables the setting.

The opt-in document is `custom.obelisk.memberChannels: { roleId, enabled }` in authenticated encrypted metadata. While the owner's Obelisk session is open, a single runtime worker issues signed Grants to joined, unbanned members, preserving their other roles. It operates only after synchronization reaches live, checks the role's exact permission/scope/rank before every Grant, backs off failures and stops with the runtime. The owner's device must be online to grant a newcomer access; this is not a server-side automatic default role. Once received, the Grant works without the owner staying online and is cached/recovered by the SDK. Before turning the setting off, the owner republishes accepted channel definitions (including deletions) authored under this role. This preserves those channels when the SDK revalidates historical authors against the revoked permission. A guard rejects concurrent channel changes during signer I/O instead of dropping that new work. The role's permissions are then zeroed; separately assigned roles remain effective.

Members with this permission use the same mobile + and channel form as the owner, including Publications and nesting. Other clients can validate the signed roles and channel editions even if they do not implement Obelisk's opt-in automation. A role edited to carry any additional privilege is never automatically assigned. The patch and regression tests keep the original concurrency checks, reject role/epoch changes during signer I/O, and report relay refusal without claiming success.

Its Members action works while viewing both chat and Publications. Remaining parity work and implementation limits, distinct from already-tested text/media/categories/Publications:

- Channel unread/mention/reply badges and encrypted read-cursor sync are integrated. Notification inbox cards, sounds, OS notifications, mute controls and phone switcher badges still need Concord integration.
- Desktop and phone search cover locally loaded accessible channels, with the latest 50 matches and channel navigation. Complete remote-history indexing and exact-message navigation remain unfinished.
- Roles can be created and assigned, but the UI does not yet offer full existing-role editing/deletion, all permission bits or channel-scoped grants.
- Channel administration still needs full description/image, privacy/access-management and deletion workflows. The user's own active invitations can be listed, copied and revoked; this is not a list of other members' secret links.
- Publications have titles, comments and nesting; the projection currently supplies empty tag/topic lists.
- Staff-readable reports, the moderation queue, separate kick/unban workflows and wider ban/private-channel rekey recovery coverage remain unfinished.
- Community emoji/sticker-pack management, games, message zaps/forwarding and external previews are not integrated for private Concord content. Existing wallet and DM features remain separate.
- Pending uploads are memory-only and do not survive reload; decrypted attachments are not persistently cached.
- Other-client interoperability for Obelisk category/parent extensions, and broader signer/relay/rekey scenarios, still require testing. AUTH-required relays are unsupported by the isolated never-auth transport.
- Voice remains deliberately unsupported until the planned protocol integration.

The member-channel opt-in also has a protocol difference: creation comes with editing/deletion authority, and new automatic Grants require the owner's Obelisk session online. Existing grants work without the owner online.

## Read state, search and invitation management

Concord read cursors live in the memory-only `store/chat/concord-read.ts` projection. The runtime seals them in the existing account-specific Concord vault under `obelisk:concord-read:v1`, and synchronizes that document as signed kind 30078, NIP-44 encrypted to self, with only its fixed `d` identifier visible. Targets are the user's discovered inbox/read relays (compatible defaults only as fallback), using the existing never-auth Concord identity. No community IDs, message text or cursor data enter plaintext localStorage or `bridgeCache`.

Cursors merge by maximum timestamp per channel/thread. Writes wait for a successful remote read, merge concurrent progress, require a relay acknowledgement and retry rejected publishes. Runtime disposal cancels observation and clears private memory. Generation ownership prevents a delayed cleanup from an older login of the same account from clearing or overwriting the newer session. Parsing rejects oversized documents, malformed coordinates and implausibly future timestamps. The document and observed channel set each cap at 512 entries, with a 60,000-byte document ceiling below the NIP-44 plaintext limit; this is a current limit, not unlimited community support. Cursors use message-second resolution like the existing NIP-29 cursor model.

Unread/mention/reply counts derive from authenticated SDK local timelines without opening additional channel subscriptions. Shared channel rows draw the ordinary badges, and Concord rail tiles show mention/reply totals. A chat advances its cursor only when its actual scroller is mounted, visible, focused, near the bottom and not covered by search, settings or the members panel. The phone community list does not mark its default channel read. New messages retain the person's scroll position when reading older history. Publication thread cursors contribute to the parent channel's aggregate without acknowledging unrelated threads. Missing cursors use the existing 24-hour bootstrap window. This does not yet implement notification inbox cards, sound/OS alerts or protocol-specific mute preferences.

Both shells expose search over locally loaded accessible channel history. Results are limited to the newest 50 matches and open the matching channel. Search uses disposable memory and closes its SDK observers when dismissed. It does not fetch complete history or transmit search terms.

Invitation settings include the signed-in account's active SDK Invite List entries, with copy and guarded revoke actions. Failed revocations stay retryable. Revoking an invite blocks future use of that link; it does not revoke existing membership or rotate community keys. The SDK retains ownership of Invite List encryption and authority checks.
