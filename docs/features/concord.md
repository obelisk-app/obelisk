# Concord integration

Status: implementation in progress on `feat/concord-dual-protocol`. This document describes the code present, not a claim of production readiness or complete protocol parity.

## Ownership

Each community uses either NIP-29 or Concord. There is no message bridge between them. Existing NIP-29 relay selection and admission remain unchanged. The existing + menu contains a Standard/Encrypted segmented selector and create/join tabs. Joined communities and NIP-29 relays share one alphabetically ordered rail without protocol sections. Concord rail tiles subscribe to authenticated community images and update when the profile image changes. Conversations render in the normal desktop or phone shell, using the existing channel rows, header, message rows, menus and composer. Only setup and administration use dialogs. The channel-header gear edits the selected channel name using an expected-edition guard, preserving its privacy and custom fields. The community-header gear opens community settings. Main community settings show invitations and appearance; channel creation and role creation have separate subviews with the shared Back header, so their fields never appear in the main form. The sidebar reuses `SidebarHeader` for its banner, icon and title, and `CreateGroupSection` for its visible + channel control. The existing appearance picker stages images locally; Save sends them through the encrypted SDK uploader, and authenticated image bytes are displayed using temporary object URLs. Route-owned integration lives in `src/app/[locale]/app/concord/`.

`src/services/nostr-bridge/concord/` owns the lazy, per-session Concord runtime. Its public entry is `getConcordForBridge` through the bridge front door. The SDK is the MIT-licensed `@applesauce/concord` snapshot `0.1.0-dev.00ceaa38355d`, vendored as `vendor/applesauce-concord-00ceaa38355d.tgz` from the Accordion reference client's dependency. The upstream revision is `00ceaa38355d6d3cbc1f7c859c0e1d5eae71e841`. The reference application's source is not copied.

`hub-socket.ts` provides the SDK's WebSocket interface over Obelisk's RelayHub. Actual sockets belong to the hub. Concord uses a separate `concord:<pubkey>:<generation>` identity with no AUTH signer and `never-auth` policy. This deliberately does not authenticate the person's account to community relays. Relays requiring AUTH are not supported by this transport yet. NIP-77 requests receive an unsupported response so the SDK can fall back to paginated Nostr REQ.

Creation requires exactly three distinct secure WebSocket relay URLs. Defaults live in `src/constants/nostr-bridge/concord.ts`. Imported communities retain the relay set defined by their protocol state. This is a Concord-specific exception to the NIP-29 single-active-relay rule, not permission to expand existing group subscriptions.

## Navigation

The address bar uses `/app#concord=<community-id>&channel=<channel-id>` (with the current locale prefix when present). Routing identifiers live in the fragment, not the request query; invitation secrets and encryption keys are never included. The old NIP-29 relay/channel coordinates are removed while viewing Concord. Reload and browser Back restore the indicated community and channel, ahead of the encrypted last-view cache. These are navigation links for existing members, not invitations granting membership. Both shells yield URL ownership and clear their watched NIP-29 channel while a Concord community is displayed.

## Storage and lifecycle

The runtime supplies encrypted SDK storage explicitly; it does not use the SDK's default localStorage persistence. IndexedDB `obelisk-concord`, object store `sealed`, holds authenticated ciphertext under an account-specific non-extractable vault key named `concord-key:<pubkey>`. Record names hash SDK keys so community identifiers are not embedded directly in cache addresses. Decrypted community state and timelines stay in runtime memory. The last selected community, channel and whether its pane is open are stored under the encrypted `obelisk/navigation` record. They restore after sign-in without overwriting a new selection or an incoming invitation. Membership storage is unchanged; a deployment does not clear it.

Rumor stores persist encrypted plane snapshots and reject growth beyond 100,000 events or 32 MiB per plane. They must fail closed rather than silently truncate authority history. Session guards reject work after account invalidation; disposal closes SDK subscriptions and removes the isolated hub identity. This storage is listed in the local-data inventory. It does not use `bridgeCache`, which stores ordinary relay-derived data in localStorage.

## Implemented surface and remaining work

The current shared chat surface has create/join forms, channel creation and selection, text sending, reactions, deletion projection and invitation generation. Clicked Concord invitations are routed through the app fragment, held only in memory, and removed from the address bar after sign-in. The invitation landing uses a full document navigation into the localized app so its CSP nonce changes with the document; the fragment is captured before login and retained until authentication. English, Spanish and Portuguese strings live in each locale's `chat.concord` subtree. Forms use the shared form model and primitives.

Channel creation supports private channels and the native Publications view. Categories use the optional `custom.obelisk.category` extension; updates preserve unknown fields and guard the selected edition head against concurrent edits. Other clients may ignore this extension. Role creation and assignment use the SDK's authority checks. Invite and deletion controls are capability-aware. Private channels without a held key are disabled. The initial ban action requires completed SDK Refounding and requires explicit review of retained readers for each private channel before rotating its key; it must not claim read-access revocation from a Banlist edit alone.

Attachments use independent AES-256-GCM keys and 16-byte nonces, carried only inside encrypted imeta. Only ciphertext goes to the existing encrypted Blossom uploader. Downloads are explicitly requested, bounded to 25 MiB plus the GCM tag, authenticated, checked against available hashes and downloaded as opaque files. Decrypted attachments are never added to a persistent cache.

Comprehensive channel/category/publication editing, broader private-channel rekeying validation, staff reports, search, notifications, games and CORD-07 voice are not yet verified or complete. The real two-account role-delegation test currently fails: the pinned SDK rejects a staff Grant after its optimistic local echo with `staff Grant delivery state changed during preparation`. Its authority guard remains intact. A proposed vendor modification was rejected by automatic approval review and was not applied. Role administration and moderation still need this defect resolved and broader browser coverage. Do not describe this implementation as full Concord parity until these paths and cross-client interoperability are tested.

## Validation and test deployment

Unit tests cover scoped identifiers, key derivation against the SDK, encrypted envelope interoperability, relay isolation, asynchronous socket replies, encrypted account storage and disposable test identities. Attachment tests reject modified ciphertext, wrong keys, incorrect hashes and unsupported algorithms. `scripts/e2e/concord/dual-protocol.spec.ts` has passed creation, clicked invitation, two-account message exchange, encrypted file upload/download and reload using fresh keys. Traces, screenshots and video are disabled because session setup contains private keys. Never commit test credentials or log invitation secrets.

The shared-shell scenario separately checks create/join through +, two-account messaging, encrypted attachments, categories, automatic selected-channel restoration, desktop/mobile layout and return to the ordinary shell. The role-delegation scenario remains a known failing regression. Run typecheck, lint, structural guards, unit tests and the browser scenarios before deployment. A visible NIP-29 shell alone does not establish NIP-29 messaging regression coverage. Live relay tests depend on relay availability and admission policy; record failures honestly.

Only deploy to the persistent `/root/obelisk-dex-test` checkout, preserving its environment files and dependency symlink. Build there and restart only PM2 `obelisk-dex-test` on port 3002. Verify `https://test.obelisk.ar` after restart. Do not use the production deploy script or create timestamped test release directories. See [operations](../operations/README.md).

## Shared component protocol boundary

`ChannelProtocolContext` routes composer send/upload, reactions and deletions to Concord. Absence of that context preserves the existing NIP-29 path. Encrypted uploads are bounded in memory and passed to the SDK uploader at send time; plaintext never enters the public Blossom uploader. Private message bodies do not auto-unfurl URLs or load public game/media previews. Public event links, forwarding and zaps are unavailable for private message IDs. Local search, rich private media rendering and full Publications parity remain follow-up work.
